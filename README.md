# ChatAnalyzer · 对话观察室

面向局域网的单用户对话分析应用。React + TypeScript 单页前端，独立 Node.js + TypeScript API，SQLite 持久化。界面参考 LiveGalGame_gc 的侧栏、对象档案、会话和设置布局，使用淡蓝与粉蓝配色；代码从头实现。

## 能力

- 自身称呼、多个别名、性格与风格；对象 QQ 绑定、标签、简介与共同群指定。
- QQ 双向私聊及指定群的实时消息（保留图片与文字的原始顺序）；新对象自动分页导入当前可读取的私聊历史，支持断点继续和重连补偿。
- 三种独立资料：可修订、覆盖更新的长期沟通画像；带来源和时间的增量事件记忆；仅供后台 AI 上下文使用的增量会话摘要。
- 同一模型更新内部摘要并判断相关性、态度、情绪及变化；默认累计 20 条或双方静默 60 秒更新。建议判断默认累计 30 条、双方静默 120 秒或明确变化时触发，无需建议也记录原因。
- 需要建议才使用关键词及 90 天尺度的时间衰减检索历史，再由同一模型生成详细建议。建议直接展示，不设置采纳状态或建议冷却。
- 新消息到来时取消旧请求并重新归纳未处理消息；暂停对象或会话可取消该范围所有 AI 请求，接收消息不受影响。
- AI API 支持 OpenAI 兼容的 `/chat/completions` JSON 输出，全应用使用同一个模型，请选择支持图片输入的多模态模型。

不提供桌面客户端、音频、麦克风、移动客户端、对话分支或代发回复选项。微信接入见 [TODO.md](TODO.md)。网页会随窄窗口调整布局。

## 两台主机的连接关系

```text
QQ 所在电脑：QQ + SnowLuma（登录仍由用户在原 QQ 客户端完成）
                      │ OneBot v11 正向 WebSocket
                      ▼
Docker 主机：ChatAnalyzer API + SQLite ← Nginx + React
                                           │
                                http://主机局域网IP:7456
```

SnowLuma 独立安装并接入原 QQ 进程；不会随 ChatAnalyzer 镜像分发。ChatAnalyzer 只允许 `get_login_info`、`get_friend_list`、`get_group_list`、`get_friend_msg_history`、`get_group_msg_history`、`get_image`，不调用发送、撤回、已读、登录、注销接口。访问事件不会触发 QQ 消息发送。

SnowLuma 是第三方桥接，客户端兼容性和影响需用户在实际环境核实。历史以接口可读范围为限，分页结束也不代表账号的全部历史；断线较久时补读达到上限会显示缺口提示，可点击继续读取。已读页会去重，带负数的消息锚点原样传递。

## 在目标主机部署

以下为待用户在目标主机执行的步骤；本项目实现期间不运行 Docker 部署测试。

1. 安装 Docker Engine / Docker Desktop 与 Compose。
2. 在项目根目录创建 `secrets/app-password.txt`，只放访问密码，至少 12 字符，建议随机生成。该目录已忽略，不要加入 Git。Linux 上限制其权限，使宿主机用户和容器 UID 1000 能读取；不要授予其他用户读取权限。
3. 执行：

   ```sh
   docker compose up -d --build
   ```

4. 浏览器访问 `http://主机局域网IP:7456`，输入上述密码。API 不直接发布宿主机端口。
5. 打开“连接设置”，填写 AI Base URL、Key、一个多模态模型名称、OneBot WebSocket 地址、Access Token 和自身 QQ 号码。
6. 填写“我的档案”，建立对象档案，读取好友后可按 QQ 号或 QQ 昵称搜索（支持部分匹配，昵称不区分大小写），再选择好友；也可手动填写 QQ，按需指定共同群号。新建或编辑档案时可选择性别、填写关系简介和长期沟通画像（喜好、忌讳与边界、沟通习惯）；未填写性别的旧档案保持为“未填写”，原简介内容保留。

### SnowLuma 配置

在 QQ 所在电脑安装 [SnowLuma 发行版](https://github.com/SnowLuma/SnowLuma/releases)，按其 [部署文档](https://snowluma.github.io/zh/docs/guide/deploy)接入已登录 QQ。为对应账号开启 OneBot v11 **正向 WebSocket 服务端**，配置强 Access Token，并允许 Docker 主机访问此端口。

开启自身消息上报 `reportSelfMessage`，否则无法观察你自己通过 PC / 手机发送的消息。事件过滤须放行 `message` 和 `message_sent`、所需私聊与群。应用通过 `get_login_info` 校验自身 QQ，防止接错账号。第一次连接失败时检查 OneBot 端口，而不是 SnowLuma WebUI 的 5099 端口。

QQ 与 Docker 在不同电脑时使用 QQ 电脑的局域网 IP；同一宿主机可使用 `ws://host.docker.internal:端口`。容器内的 `127.0.0.1` 指向容器本身。QQ 主机 IP 改变后需更新设置。

### 数据与密钥

`chat_data` 卷保存 `chat.sqlite`、WAL 文件及 `master.key`。API Key 和 OneBot Token 使用 AES-256-GCM 加密；主密钥位于同一受保护卷中，主要防止数据库单独泄露，不防止整卷泄露。备份时停止 API，再备份整个卷；恢复必须同时恢复数据库与主密钥。聊天原文和记忆本身没有加密，应限制主机与备份访问权限。

访问密码来自 Compose secret，登录会话只存于进程内存，24 小时过期；重启 API 会退出登录。密码变更后重启 API。使用局域网 HTTP 时通信未加密；需要跨不可信网络访问时在前面配置 HTTPS。应用不接收 QQ 密码或登录凭证。

更换自身 QQ 账号需使用独立数据卷，避免不同账号消息混入已有档案。对象 QQ 绑定同样不可直接替换。停用对象分析使用暂停按钮；本版不提供批量删除数据的界面。

### 使用与故障定位

- 先设置连接，再建档。连接尚未就绪时档案保留，连接成功后自动导入。
- AI 设置中的“测试 AI API”会使用当前表单的 Base URL、模型和 Key；Key 留空时使用后端已保存的 Key。无需先保存，测试也不会保存配置。测试发送固定消息并校验 JSON 回传，不提交聊天内容或验证图片识别，会产生一次模型调用。
- 测试成功会提示“测试成功”；失败显示“连接失败”和具体步骤：配置校验、发送请求、HTTP 响应、读取回传、解析回传或校验模型输出。HTTP 错误附状态码，原始供应商响应与密钥不会返回页面。测试最多等待 45 秒；修改 AI 配置、离开设置页或关闭应用会取消在途测试。
- 连接测试成功仅代表固定测试消息调用与 JSON 回传成功，不保证实际分析的输出字段、图片输入、长上下文或证据归属校验都能通过。实际分析使用已保存配置，测试新配置后还需保存；测试不会清除会话原有错误或自动重试分析。
- 分析失败提示会标明摘要更新、建议必要性判断、详细建议生成或画像与记忆归纳阶段，并区分请求步骤、图片读取、输出字段、画像证据、记忆主体和记忆证据问题。证据不符时整批归纳结果不保存，保留进度供重试；不会把问题一律归为 API 设置错误。
- 对象详情页的“AI 调用状态”可展开查看当前会话的执行时间线：消息合并、摘要、建议判断、图片地址读取（有文件标识时调用 `get_image`）、AI 请求与回传解析、记忆检索、证据校验和结果保存。每步显示状态、起止时间与耗时，跳过建议时显示原因，取消或失败也保留记录。这些是应用执行事件，不展示模型内部思维内容或原始提示词。
- 执行记录约每 2 秒随详情刷新；每个会话只保留最近 5 轮、每轮最近 80 个步骤，保存在内存，应用重启后清空。不同对象及会话隔离，记录不包含聊天正文、图片地址、密钥或供应商原始响应。
- 对话页按消息发送时间选取最近 200 条，并从上到下按旧到新排列；时间相同的消息按入库序号稳定排序。历史补读不会挤掉发送时间更新的消息，AI 检查点仍按入库序号独立推进。
- “历史记忆”可查看可读范围及继续读取；“重新检查”重试摘要或归纳失败。失败批次不推进相应进度。
- 未相关群消息只用于局部上下文，不写入对象摘要或事件；群聊判断依赖模型，仍可能误判。
- 对话工作区展示态度、情绪变化与原因，以及是否生成建议的结果与原因，不展示内部对话摘要。如需完全停止 AI，请暂停对象或会话。
- 原始消息、图片内容、摘要、画像和检索记忆会提交到你配置的 AI 服务；选择合适的服务与模型。模型需支持图片输入与 JSON 格式输出。
- 消息合并窗口默认为 60 秒，新消息会重新计时；窗口结束只检查是否满足分析条件，不再每次都调用 AI。摘要默认累计 20 条或静默 60 秒触发；建议判断默认累计 30 条或静默 120 秒触发，摘要发现明显变化也可触发；画像、记忆归纳与重要事件提取默认累计 100 条或静默 600 秒触发。设置界面可分别调整这些条数和静默时长，条数与静默任一满足即可触发，达到条数阈值不必等待合并窗口。
- 三个阶段分别维护消息进度；建议或归纳到期时会先补齐内部摘要，确保使用最新上下文。仅历史消息不触发建议，归纳失败不回退已成功的摘要进度。点击“重新检查”可立即重试各阶段积压。静默计时以最近一次消息或重新安排分析为起点；恢复或重启会重新计时。没有新增待处理消息不会重复调用对应阶段。静默检查会等待当前任务完成，新消息则取消旧请求；供应商可能对已接收请求计费，取消不保证费用退回。
- 内部摘要采用递归压缩：同一次摘要调用先把上一轮合并摘要进一步压缩，再加上本批新摘要，不增加独立压缩请求。旧部分最多保留上一轮长度的 65%，且不超过 600 字符；新部分最多 380 字符，合并摘要限制在 1,000 字符以内。优先保留仍未解决的问题、约定、边界和重要变化，逐轮淡化已解决的旧细节。语义取舍依赖模型，压缩不能保证完全无损；原始消息、画像和事件记忆不会因此删除。旧版最多 6,000 字符的摘要会在下一次相关摘要成功更新时转为新格式；超长或无效输出不保存，也不推进摘要检查点。
- 摘要衔接从检查点之前最多 24 条已处理消息中筛选，结合本批开头的指代、承接问题、词语重合及双方身份，最多携带 4 条，每条文字节选最多 600 字符；不再固定附带最近 10 条。此筛选使用本地规则，无法保证找回较远的引用或所有语义关联。
- 建议必要性判断主要携带紧凑摘要、最新态度与情绪及其变化、最近 3 个指标节点，以及最多 6 条证据消息（每条文字节选最多 500 字符）。优先选择明显变化批次的来源和双方近期发言，并标明消息总数与节选数量；需要详细建议时再携带较完整的近期原始消息和检索历史。
- 画像与记忆归纳仅携带本批原始消息、必要身份、相关画像字段和候选重复记忆，不再重复附带完整档案及会话摘要。画像按话题词语重合及喜好／边界／沟通线索选取；空字段允许新增资料，模型只返回有证据的字段修改，未提供及未修改字段保持不变，用户在请求期间的修订继续优先保留。
- 候选重复记忆从同一对象的全部已保存记忆中，用消息来源重合、关键词和中英文词语重合筛选，最多 8 条、正文合计最多 6,000 字符，不按“最近 60 条”截取，也不让时间衰减排除旧的重复候选。检索无需额外 AI 请求，不使用向量服务；措辞差异较大时可能漏检。候选只是供模型比对，模型仍须区分重复事件、新进展和相似但不同的事件；本地检索本身不删除或合并记忆。图片仍沿用现有图文传入方式，未增加图片描述缓存或图片压缩策略。
- 图片与图像形式的表情包直接作为多模态图片输入，和文字按消息时间、消息内段落顺序交错传入；保留消息 ID、发送者 QQ、身份和时间，不把图片统一追加到上下文末尾。QQ 系统表情保留其 ID 作为文字标记。无需独立视觉模型或 OCR 服务。
- 通过 SnowLuma 的只读 [`get_image`](https://snowluma.github.io/zh/docs/api/extended/get_image) 获取图片 URL，由 ChatAnalyzer 后端下载和真实解码，缩放至最长边 1920 像素并转换为 JPEG 或 PNG，使用兼容协议的 [`image_url`](https://developers.openai.com/api/docs/guides/images-vision) Base64 数据输入。AI 服务无需再访问 QQ 图片直链；图片处理、错误分类均不依赖特定 AI 服务商或模型名称。图片仍保留在原消息的图文位置，重复图片只下载处理一次。
- 下载仅允许 QQ 公网图片域名（qq.com、qq.com.cn、qpic.cn、qlogo.cn、gtimg.cn、gtimg.com 及其子域）的默认 HTTP(S) 端口，实际连接时校验 DNS 公网地址，不跟随重定向，不携带 AI Key。图片只在内存处理，不读取 QQ 主机的本地路径或保存图片文件；QQ 与 API 无需共享目录。支持读取 JPEG、PNG、WebP、GIF；动图只发送首帧，并在对应图片旁标注未分析完整动画。过期页面、损坏图片和不支持的格式会在提交 AI 前明确失败。
- 单次分析最多 100 张图片，单张下载上限 10 MiB、下载超时 10 秒、解码像素上限 4000 万且处理上限 5 秒；标准化后单张上限 4 MiB、整次图片合计上限 12 MiB（重复位置同样计入请求体），请求体上限 24 MiB。取图和 AI 请求共享 45 秒超时。失败不把缺失图片冒充已识别内容，也不推进失败阶段的检查点；可在恢复连接后重新检查。暂停、新消息和应用关闭会取消请求；已开始的原生解码任务在时间限制内收尾，结果不会提交 AI。
- HTTP 400 会有界读取并分类通用供应商错误（嵌套 error 对象或顶层 code/message），区分图片、上下文、JSON 输出模式和参数问题。仅显示本地生成的分类说明，不返回原始供应商消息、图片链接或密钥，不按某家供应商的错误编号硬编码含义；未知格式仍保留 HTTP 状态与通用提示。
- 图片顺序信息适用于更新后接收或首次导入的消息；旧版已保存为 `[image]` 等占位文字的记录缺少图片标识，无法自动还原，重复导入也不会覆盖既有去重记录。
- 旧版双模型配置会优先沿用原完整分析／归纳模型；若只有轻量模型则沿用它，新配置的模型名称优先。摘要、建议判断、详细建议和记忆归纳均使用该模型。
- 已保存的合并窗口、建议条数和静默时间继续保留；缺少的新增设置使用上述默认值。旧采纳状态及冷却字段不再生效，无需清空数据库。
- 画像与记忆按独立的归纳静默时间或数量阈值更新（也可手动重新检查）；普通闲聊不新增事件。画像字段更新后只保留最新版本。归纳按 QQ 身份区分用户、当前对象及其他群成员；变更画像字段和新增事件均须引用本批消息，且至少包含对象本人发言。主体不符或来源无效时整批归纳失败，保留进度供重试。仅用户单方面描述的对象事实暂不自动归档；模型仍可能误读引用或混合语境，需人工核对。
- 重要性由归纳模型按高门槛筛选：仅保留对对象生活、双方关系或后续相处有持续影响的重要生活节点、待履行约定、关系变化及显著情绪节点；没有符合项时返回空记忆。普通技术问答、功能咨询、操作说明、报错排查和一次性信息交换不归档，不能因为多轮交流或对象回复就视为重要。技术话题涉及明确的重要后果或具体约定时，只提取该后果或约定。该语义筛选依赖模型，后端身份及来源校验不等于重要性校验。
- 此归属校验只作用于后续归纳，不自动清洗既有画像或历史记忆；已有错误画像可通过“修订画像”纠正。“重新检查”只重试未处理批次，不会重建已归档记忆。
- 查看状态：`docker compose ps`；查看安全日志：`docker compose logs --tail=100 api`。不要把真实密钥粘贴进日志或反馈。

## 本地开发与验证

Node.js >=22.14（使用内置 `node:sqlite`，Node 22 可能提示实验特性）。

```sh
npm ci
npm run typecheck
npm test
npm run build
```

开发前也需创建本机 secret 文件。分别运行 `npm run dev:api` 和 `npm run dev:web`，打开 Vite 地址。开发代理将 `/api` 转发到本机 3000。`npm start` 只启动独立 API，前端由 Nginx 或 Vite 提供。

测试隔离真实 QQ 和 AI，覆盖图文顺序、多图片请求、取图失败与取消、消息规范化、只读动作、认证、秘密落盘、去重、取消过期结果、暂停、独立阶段节流和建议分级。真实 QQ/模型兼容性、Docker 构建及其他主机的网络与挂载权限仍需目标环境验证。

## 结构

`shared/schema.ts` 定义跨层契约；`server/store.ts` 管理持久化和加密；`bridge.ts` 管理只读 WebSocket；`ai.ts` 封装模型；`engine.ts` 管理分析任务；`application.ts` 编排导入和生命周期；`http.ts` 提供认证 API；`web/` 为 React 界面。
